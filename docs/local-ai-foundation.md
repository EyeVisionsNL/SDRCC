# Local AI — SDRCC 0.80.7 Reception Analytics

Local AI is optional. No model download, runtime, database or AI background task is required to use SDRCC. New installations offer a disabled-by-default checkbox. Existing installations update normally using System → Advanced Maintenance → SDRCC Update; the new Intelligence tab offers a separate explicit install action. Existing feature selections remain unchanged.

## Intelligence

Open the Intelligence tab (before Reception Analytics, after Mission Analytics when satellites are installed). All Local AI installation, removal and settings are managed there; Advanced Maintenance retains the ordinary SDRCC update controls.

- Install Local AI: downloads the verified CPU build of llama.cpp and Qwen3-4B Q4_K_M (~2.5 GB model).
- Enable / Disable / Remove Local AI: removal affects only AI assets and settings.
- AI Settings: CPU threads (1–4, limited by available CPUs), maximum answer length (128–512 tokens). Default: 2 threads where available, 384 tokens, 4096 context, thinking off. Address space limit: 5–8 GiB (default 7 GiB); this is virtual address space, not reserved physical RAM. Native engine diagnostics are available in the SDRCC service journal.
- Ask SDRCC: local single-turn questions in your language. Read-only Reception Analytics evidence is available for 24h, 7d and 30d windows. Auto recognizes common English/Dutch reception questions and period phrases; choose a period explicitly or select No reception data. Verified source values are displayed separately from the AI answer.

## Hardware and safety

16 GB RAM recommended. At least 7 GiB detected total and 6 GiB available RAM, two CPU threads, and 5 GiB free disk space for initial installation. The runtime refuses new requests under high load. The AI engine starts for a question and exits afterwards; CPU-only, low scheduling priority, bounded address space and CPU time. The first release does not provide a continuous AI service or hard CPU quota. Actual performance and compatible Linux builds must be verified on the target hardware. ARM64 AI is experimental and does not change SDRCC's supported platform requirements.

No cloud inference, arbitrary commands, receiver control, automatic restart, live AIS/ADS-B, ATIS or mission execution. Only bounded station-wide Reception Analytics historical summaries are available. Keep the dashboard on a trusted private network. Reception always has priority. The model is not redownloaded on an ordinary SDRCC update.

Model/runtime are stored under `data/local_ai/`; configuration uses the existing optional features file. The full SDRCC uninstaller removes project data; optional removal in Intelligence removes just AI assets and settings.

## Read-only SDRCC intelligence (Reception Analytics implemented; later phases planned)

Reuse the station's existing sources. No duplicate database or additional RF receiver.

1. **Reception Analytics first.** Source: `data/analytics/reception.sqlite3`, table `samples` in `core/reception_analytics.py`. It samples nominally once per minute and retains 90 days. Implemented fixed, parameterized queries over 24h/7d/30d periods for mean and peak fresh AIS targets, ADS-B targets, rates and range. Count only valid active observations; exclude null and legacy unvalidated AIS totals. Report actual sample count, time range, coverage and source. A mean of simultaneous targets is not a count of unique vessels. A station-wide average is not a Vlaardingen-specific average.
2. **Live reception and ATIS.** Read the existing `core/traffic_map.py` snapshot and `data/analytics/atis_statistics.sqlite3` (table `atis_events` in `core/atis_statistics.py`). Reuse existing freshness/identity validation. Filter current positions by explicit radius or defined area; never invent historical geographic counts from aggregate samples. Add ATIS totals and matching status only where recorded. Respect selected/installed features and distinguish stopped, stale, unavailable and zero.
3. **Mission history, emergency and local memory.** Reuse `core/mission_history.py` and read-only emergency history/snapshots. Add a separate optional AI memory database only after defining its schema, retention, size limits, delete/export and consent. Do not change existing collector retention or store full live feeds by default.

### Data access contract

- Reception reads have a 60,000-row cap, 1.5-second SQLite progress deadline and 300 ms lock timeout. No new history database is created. Coverage is sample count divided by nominal expected count (capped at 100%); it is not an uptime measurement. Missing, null, inactive and legacy unvalidated observations are not interpreted as zero.
- Open existing SQLite databases with URI `mode=ro` and `PRAGMA query_only=ON`; do not call helpers that perform schema creation/migration or resets. No database created by the AI when the source is missing. Use fixed queries, parameter binding, restricted periods, row limits and execution timeouts; no SQL, shell commands, arbitrary paths or arbitrary URLs generated by the model.
- A deterministic data adapter computes numerical results. Pass a bounded structured evidence payload to Qwen with source and timestamps; treat source text as data, not instructions. The answer must distinguish observed values, estimates and unavailable data. Display evidence independently of the model response.
- AI remains optional, local-only and on-demand. It cannot start/stop services, change receiver allocation, reset analytics, edit files or execute missions. Mission Engine remains the sole execution authority.
- Test read-only opening, missing databases, disabled modules, null/zero semantics, legacy schema, bounded query execution, time windows, stale observations and no changes to existing data. Run existing release/manifest/3D map checks before releasing on develop. Test on the actual station with AI enabled and disabled before promotion to main.

## Station Health and Maritime Intelligence (0.80.9)

Intelligence subviews provide explicit read-only snapshots via Refresh and an optional local AI assessment. Opening a subview reads current observations if AI is enabled. No polling daemon, no additional receiver ownership, no service changes. Station Health checks configured USB identity, service state, decoder output, available RAM, free disk, load, CPU temperature where available, reception history freshness, and classified visible log messages over the last hour (150 entries per unit, 64 KiB SDRCC log). Stopped services may be intentional; a kernel USB identity check is not a transfer test, and a database read is not a full integrity check. Log counts represent matching messages, not unique incidents.

Maritime Intelligence uses local AIS-Catcher reports no older than 300 seconds with validated identity and position, excluding fixed stations and non-vessels. Choose 10/25/50/100 km from configured Home Position. Vessel profiles are SDRCC display hints, not verified classifications. A limited set of ordinary vessel examples is shown; counts refer only to received reports. ATIS history is station-wide over the last 24 hours and is read without migrations; missing fields and disabled modules are reported separately. No live voice transcription, full traffic coverage, geofencing history or automatic alerts in this release.

## Reception Performance and Mission Analyst (0.80.10)

Reception Performance compares the rolling last 24 hours with the preceding seven days, without overlap. Read-only reception summaries show active-sample means, peaks and valid sample counts; AIS legacy/unvalidated measurements are excluded. Percentage comparisons require at least 50% nominal sample coverage in each window, 60 valid samples and valid observations for at least half the active samples for each metric. Stale current history and zero baseline suppress percentages. A 10% change threshold is descriptive only: traffic volume, mission activity, propagation and RF configuration can differ. The two bounded queries are separate snapshots. The displayed rate bars use a shared scale within each pair.

Mission Analyst reads the atomically published mission_history.json directly without creating lock or history files. It aggregates up to 500 retained records (8 MiB limit), filters by all retained missions or the last 7/30 days based on recorded end time, excludes identifiable simulator records, reports undated records and excludes cancelled/unknown outcomes from the success denominator. Missing measurements remain unavailable; SNR, images, frames, quality and duration have explicit sample counts where relevant. Satellite and receiver tables show up to eight groups each, plus omitted group counts; maximum elevation bands are 0–<30, 30–<60 and 60–90 degrees. Group observations are not controlled experiments. No live mission control, future pass predictions or recording/image inspection. AI assessment remains explicitly on demand.

## Aviation Intelligence and Station Memory (0.80.11)

Aviation Intelligence reads bounded fresh local readsb aircraft/statistics files only while ADS-B is active. A positioned aircraft requires valid identity and coordinates, explicit position and message age <=30 seconds and snapshot age <=5 seconds. Radius 10/25/50/100/200 km uses Home Position and great-circle distance. Aggregate counts, rotorcraft classification, explicitly reported ground aircraft, altitude bands, speed, maximum range and station-wide last-minute message rate are shown. Surface categories are excluded. No individual aircraft identifiers, positions, tracking or external lookups are provided to AI. Missing/stale data is unavailable, not zero.

Station Memory stores explicit operator notes (incident, hardware, configuration, note) and manually imported fixed classifications of recent visible receiver logs in data/state/station_memory.sqlite3 (new file mode 0600). It is separate from downloadable AI assets and persists when AI is disabled or the model removed. Opening and searching are read-only and do not create an empty database. Import scans the last 24 hours within 64 KiB SDRCC log and 200 visible journal entries per receiver service, with at most 200 matching classified records per import. Repeated log entries are deduplicated; multiple messages may describe one incident. No raw logs or serials are copied into the notebook. Deleted imported records can reappear if explicitly imported again. Capacity 1,000 entries, no silent eviction. Search is literal and paginated, ten records per page. AI sees at most six entries from the selected page, with shortened detail/outcome fields. Manual note text is operator-provided, not verified. Only explicit operator actions write; AI inference never writes, controls receivers or starts missions. No background collection, automatic diagnosis persistence, or automatic before/after RF comparison yet.

## Anomaly Detection (0.80.12)

A low-cost worker checks every 60 seconds while Local AI is installed and enabled; the monitor can be paused independently. No Qwen inference is scheduled. The worker pauses during SDRCC updates and does not change services, receiver bindings, scheduler or missions. It observes configured USB identity, AIS/ADS-B service failure and exhausted crash recovery, history freshness, RAM, disk, temperature and load. Idle or unknown observations never prove recovery. Three consecutive bad readings open an episode, three normal readings clear it; gaps and unknown/hold readings reset confirmation. Resource recovery thresholds use hysteresis (RAM/disk >=3 GiB, temperature <=78 C, load <=1 per CPU; warning <2 GiB, >=85 C, >=1.5 per CPU). History warning age >180 s. Reception-rate warnings compare a 15-minute active-sample mean with the median of equivalent UTC windows in the preceding seven days, requiring >=10 valid samples per window and >=3 prior days, baseline >=1 msg/s. Warn at <=40% of baseline, clear at >=60%; these are advisory observations, not diagnosed RF faults. No rates are compared when the service is inactive. No synthetic zeros or legacy unvalidated AIS samples. Station Memory records opened/cleared episodes with idempotent keys, no raw logs; persistent bounded outbox retries failed writes and reports capacity problems without silently deleting notes. Monitor state is stored in data/state/anomaly_monitor.json, with 40 recent transitions and up to 80 pending memory writes. Streaks restart after process restart; active episodes persist. MQTT is off by default, opt-in and best effort for new transitions only, using the existing connected Emergency Monitor broker and a separate non-retained topic sdrcc/intelligence/anomalies. The Emergency Monitor topic and alarm history are unchanged. The Intelligence badge counts open episodes; the anomaly view shows latest stored measurements and thresholds, and Analyze with AI remains on demand. No Home Assistant automation is installed by SDRCC.

## Daily Briefing (0.80.13)

Daily Briefing combines reception sample counts, active-sample means and peaks, maximum sampled range, ATIS events, stored mission results and retained technical alert transitions into a single read-only overview. The rolling last 24 hours is available on request. The background archive worker checks every five minutes while Local AI is enabled and installed and no update is underway. It creates the preceding completed UTC day's report once, after 00:05 UTC; on startup it can create that previous day's report, but does not fabricate missed older reports. The common 24-hour interval is start-exclusive/end-inclusive. Source snapshots are read independently. Archived reports are immutable and retain source availability and sampling coverage; they do not prove complete station uptime. Anomaly history is bounded to the monitor's last 40 transitions, and zero visible openings does not establish zero incidents. The reports are stored in data/state/daily_briefings/ as dated JSON (mode 0600, atomic no-overwrite publication). The 30 newest report files are retained; no model output or raw logs are saved. Missing sources and missing metrics remain distinguishable from zero. The UI allows selection of available reports, and AI assessment is explicit and on demand. No automatic inference, MQTT briefing delivery or receiver control.

## Mission Advisor (0.80.14)

Mission Advisor reads policy-approved future passes from the existing Mission Planner for the next 24 or 48 hours. It does not call the mutable queue projection or prune operator overrides. It reads bounded queue overrides and scheduler state, assigned receiver identity/presence, binding/recovery status and existing local TLE status. It flags skipped or execution-disabled passes, stale/invalid TLE, unassigned/missing receivers, binding/recovery issues and overlapping non-skipped executable windows on the single automation lane. Shared receiver roles are shown as possible interruptions, not confirmed conflicts. Highest unflagged elevation is geometry only; no guarantee of future receiver availability or reception, no preflight/handover timing or pinned active-job projection. Scheduler mode is descriptive. Historical evidence is restricted to retained known completed, non-simulation missions in the preceding 90 days, matching satellite, pipeline, receiver (serial where available, canonical/runtime alias otherwise) and elevation band (below 30, 30–<60, 60–90 degrees). Success fraction and mean peak SNR require at least three completed missions or three SNR samples respectively, and are not predictive probabilities. The UI lists up to 24 chronological passes, with best unflagged geometry across all bounded candidates (max 200). The AI receives at most six chronological displayed passes plus best geometry. No external data fetch, receiver actions, priority changes, scheduling or background inference.

## RF Optimization (0.80.15)

Record an operator-performed RF change immediately after completion: select AIS or ADS-B, antenna/LNA/splitter/gain/filter/cable/other, a 24h or 7d window per side, title and before/after details. Changes affecting both services must be recorded separately. No physical settings are changed by this feature. The baseline ends 15 minutes before the recorded timestamp and is frozen on record; the after window starts 15 minutes after it and has the same duration. No partial percentage comparison is produced before the full after window ends. Both windows require at least 75% nominal sample coverage, active samples for 75% of expected minutes, valid measurements for 75% of active samples and fresh endpoints; zero baseline suppresses percent changes. Recorded additional changes for the same service anywhere in the two-window interval suppress percentages. Undocumented changes, deleted experiment records, traffic, RF propagation and scheduling can still confound comparisons. Targets are simultaneous sampled counts, not unique totals. Range is sampled maximum range in NM. Equal-length windows do not make an observational experiment controlled. Up to 100 experiments are stored in a separate table in the Station Memory SQLite database, with a linked notebook entry inserted atomically. Refresh reads the selected experiment and the live historical after window; Save result explicitly freezes observations (even if insufficient) and updates its linked note if still present. Deleting an experiment retains the note, but removes the experiment from subsequent overlap checks. No automatic result collection or model inference, and the after window can become unavailable if analytics are reset or historical samples expire. Saved results and baselines remain intact. AI receives only the selected experiment, not the entire experiment list.
